# Движок для перезапуска: варианты

Что нужно от нового движка — по итогам разбора старого (`docs/mechanics.md`, `docs/quests.md`, `content/`):

- **Жанр.** По сути это текстовая многопользовательская игра (MUD): ~1400 локаций с выходами, NPC, предметы, диалоги, чат, кланы. Графики и физики нет, синхронизации кадров нет. «Реальное время» — это только паузы между ударами (секунды), таймеры респауна и чат.
- **Масштаб.** Один мир, десятки — первые сотни игроков онлайн. Производительность не критична, критичны надёжность и простота.
- **Клиенты.** Сначала веб (как сейчас), потом мобильные приложения iOS/Android. Значит, сервер отдаёт JSON (или шлёт события по WebSocket), а экраны рисует клиент.
- **Данные уже есть.** `content/` — UTF-8 JSON с именованными полями; движок должен читать его напрямую.
- **Правила.** ~30 формул (параметры боя, попадание, урон, каст, регенерация, опыт, цены) + рецепты-таблицы + ~10 шаблонов квестов вместо 286 `eval:`. Всё это — чистые функции, их надо покрыть тестами.
- **Безопасность с нуля.** Токены сессий вместо пароля в ссылках, хеширование паролей, роли вместо «админ по логину», никакого `extract($_GET)` и кода в данных, сервер проверяет каждое действие (в т. ч. что тема диалога была доступна).
- **Команда.** Вы + Claude. Язык и стек должны хорошо поддерживаться, иметь много готового и легко проверяться тестами.

## Варианты

### A. TypeScript: Node.js + PostgreSQL + WebSocket; клиенты React (веб) и React Native/Expo (мобильные) — **рекомендую**

- Один язык на сервере и клиентах. Типы данных и правила (формулы, валидация диалогов) — общий пакет: клиент показывает то же, что посчитает сервер.
- JSON из `content/` ложится в типы TypeScript почти без преобразований; схему можно описать один раз (например, Zod) и проверять контент в CI.
- Мобильные приложения через Expo: один код на iOS и Android, публикация в сторы, push-уведомления («на вас напали», «сообщение от игрока»).
- Сервер: Fastify или NestJS, PostgreSQL (игроки, инвентарь, состояние мира — таблицы с явными полями вместо строк `a|b|c`), WebSocket для чата и событий боя. Railway это поддерживает, переезд не нужен.
- Минус: переписывание с нуля, из старого кода переносятся только правила и данные.

### B. Современный PHP (Laravel) + PostgreSQL; мобильные — отдельно (Flutter или React Native)

- Ближе всего к исходнику: можно переносить по частям, копируя логику из `game/1`.
- Laravel даёт из коробки авторизацию, очереди, планировщик, WebSocket (Reverb).
- Минус: два языка (PHP на сервере, Dart/TS в приложении), правила не разделить с клиентом. Главный выигрыш «переносить по кускам» небольшой: старый код построен на глобальных переменных и `eval`, его всё равно придётся переписывать, а не адаптировать.

### C. Go-сервер + Flutter-клиент

- Быстрый сервер одним бинарником, Flutter — сильный фреймворк для мобильных.
- Минус: два языка без общего кода; скорость Go для этого масштаба не нужна; меньше готовых решений для веб-клиента.

### D. Готовый игровой сервер: Nakama (Go, логика на TypeScript/Lua) или Colyseus (TypeScript)

- Nakama даёт аккаунты, чат, группы (кланы), друзей, хранилище, рейтинги, уведомления. Colyseus — комнаты с синхронизацией состояния (комната = локация).
- Минус: они сделаны под матчи и синхронизацию состояния, а нашей игре нужна в первую очередь модель мира (локации, NPC, предметы, таймеры) — её всё равно писать самим, подстраиваясь под чужую архитектуру. Nakama имеет смысл, если чат/кланы/друзья станут центром игры.

### E. Готовый движок для MUD: Evennia (Python/Django)

- Сделан ровно под этот жанр: комнаты, выходы, объекты, NPC, скрипты-таймеры, каналы чата, аккаунты, веб-клиент по WebSocket, хранение в БД.
- Минус: интерфейс рассчитан на команды текстом («go north», «attack rat»), а у нас меню ссылок и кнопок; мобильное приложение будет обёрткой веба; объектная модель тяжёлая, и половину механик придётся встраивать в её «typeclasses».

## Сравнение

| | A. TS + RN | B. Laravel | C. Go + Flutter | D. Nakama | E. Evennia |
|---|---|---|---|---|---|
| Языков в проекте | 1 | 2 | 2 | 1–2 | 1 (+клиент) |
| Общие правила сервер/клиент | да | нет | нет | частично | нет |
| Мобильные приложения | Expo, нативно | отдельный проект | Flutter, нативно | SDK под клиенты | веб-обёртка |
| Модель мира (локации, NPC, таймеры) | пишем сами | пишем сами | пишем сами | пишем сами, под их API | есть готовая |

| Объём работы до играбельной версии | средний | средний | выше среднего | средний | ниже среднего, но с компромиссами UI |

## Как переносить, независимо от выбора

1. **Сначала паритет, потом баланс.** Первая версия нового движка повторяет правила старого (включая спорные — штраф `−rand(0,5)`, потерю вещей при смерти), каждое изменение баланса — отдельным решением с флагом.
2. **Паритетные тесты по старому коду.** Старый движок остаётся эталоном: формулы (`calcparam`, попадание, урон, цены, опыт) прогоняются на тысячах случайных персонажей и в PHP, и в новом движке — результаты должны совпадать. Это надёжнее, чем сверять по документу.
3. **Порядок:** модель данных и загрузка `content/` → аккаунты и сессии → перемещение и локации → предметы и торговля → бой → навыки и крафт → диалоги и квесты (декларативно) → чат и кланы → мобильный клиент.
4. **Старый стенд** остаётся приватным (за паролем Railway) как эталон для сравнения; его дыры не чиним (решение 28.09).
